# RepoBrain Demo and Evidence Contract

Status: Living demo contract — updated through semantic tenant memory and evaluation proof

## Hero demo questions

The demo will use `pallets/flask` after a concrete snapshot SHA is pinned.

### Hero question 1: impact analysis

```text
What files and modules are affected if src/flask/app.py changes?
```

The system must demonstrate:

- At least one multi-hop dependency path, if the selected snapshot contains one.
- Distance-ranked dependents.
- A visible witness path.
- A warning when a relationship is static or inferred rather than verified at runtime.

If this exact file does not produce a useful path in the selected snapshot, choose another real core file during ingestion and record the replacement in the demo notes. Do not manufacture a result.

### Hero question 2: reviewer recommendation

```text
Who should review changes to the files involved in this impact analysis, and why?
```

The system must show:

- Ranked people.
- Number of covered files.
- Recent commits.
- Review history.
- Evidence links.
- Exclusion of bots.
- Exclusion of the pull-request author when a pull-request context exists.

### Hero question 3: decision tracing

```text
Why was the current application or request-handling design chosen, and was an earlier decision replaced?
```

The system must show:

- A source pull request, issue, or comment.
- Supporting excerpt or source span.
- Decision status.
- Any superseded decision only when the relationship is evidence-backed.
- Uncertainty when no explicit supersession evidence exists.

## Three-minute demo sequence

1. Show FalkorDB and the graph model.
2. Show the pinned repository snapshot.
3. Ask the impact question.
4. Open a returned graph path and source evidence.
5. Ask for reviewers for the affected files.
6. Open the score breakdown and supporting commits.
7. Ask the decision question.
8. Open the source PR or issue and supporting excerpt.
9. Switch to a second demo tenant and show that its findings are separate.
10. Restart the application and show semantic memory recall from a paraphrased question.
11. Briefly show the MCP tool call log.
12. Close with the statement that an unavailable or empty graph produces an explicit evidence failure rather than a fabricated answer.

## Evidence levels

### Verified

Directly represented in cached GitHub or Git data.

Examples:

- A commit touched a file.
- A person reviewed a pull request.
- A comment contains an identified file mention.

### Derived

Computed deterministically from the graph.

Examples:

- A file is three dependency hops away.
- A reviewer covers four changed files.
- A file received a PageRank score.

Derived results must include the query template, parameters, snapshot ID, and score inputs where applicable.

### Inferred

Generated by an LLM from returned evidence.

Examples:

- A person appears to be the safest reviewer.
- A later decision likely replaced an earlier one.

Inferred conclusions must be labeled and cannot be presented as verified facts.

## Required answer shape

Every answer should contain:

```text
Answer
Evidence classification
Supporting sources
Graph paths or score explanation
Snapshot timestamp
Warnings and uncertainty
```

## Failure behavior

The agent must produce explicit warnings for:

- No matching graph entities.
- Missing source evidence.
- Stale findings.
- Conflicting claims.
- Unresolved identities.
- Inferred dependency edges.
- Tool timeouts.
- Incomplete ingestion.

The agent must not silently substitute general LLM knowledge.

## Features excluded from the primary demo

- Autonomous GitHub writes.
- Arbitrary repositories.
- Full issue triage.
- General-purpose multi-agent planning.
- Large-scale refresh during the live presentation.
